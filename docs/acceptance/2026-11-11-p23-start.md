# P1 确认修复与 P2/P3 首批实施记录

日期：2026-11-11。用户要求修复 P1 未通过项，并开始 P2/P3。本轮没有把“开始实施”写成 P2/P3 全量验收，也没有把 Codex 的原生 ask 能力改成支持。

## P1 确认流程修复

新增 **ASGP 调用审批**：需确认规则在真正的 PreToolUse 中提交请求，绑定设备、产品版本、会话、调用 ID 和完整参数 SHA-256。授权控制台操作员批准后才返回 allow；拒绝、到期、控制面/网络故障或回执不匹配都返回 deny。普通 observe 路径仍不访问网络。

测试机 Codex 0.166.0、Claude Code 2.1.152 使用 StepFun，真实运行以下六种情况：

| 产品 | ASGP 批准 | ASGP 拒绝 | ASGP 超时 |
| --- | --- | --- | --- |
| Codex | 待审批期间无 proof，批准后内容正确 | proof 不存在 | proof 不存在 |
| Claude | 待审批期间无 proof，批准后内容正确 | proof 不存在 | proof 不存在 |

六项全部通过，见 [审批实测 JSON](p23-approval-evidence.json)。自动化验收程序作为已认证控制台测试操作员作出接受/拒绝，不冒充真人批准；另外浏览器按钮也验证了真实 API 的批准操作。

Python 3.10 无法直接解析控制面回执的 UTC `Z` 后缀，首次联调的批准被保守拒绝；修复后六项全部重跑通过。失败运行没有作为通过证据。

Codex 的原生 `permissionDecision=ask` 仍不支持；新增字段 `mediated_approval_supported` 和 `mediated_approval_protocol` 单独声明平台审批。原生能力和平台审批不会混成一个 capability。若原 A1 被理解为每个产品都必须原生 ask，技术事实仍不满足，不能通过修改报告豁免；本轮修复的是用户可实际使用的确认流程。

端侧启用 `approval_mode=control_plane`，PreToolUse timeout 为 25 秒，审批截止最多 20 秒；SessionEnd 仍 3 秒。测试结束后恢复 observe，测试机不常驻全量阻断规则。审批只上传调用标识和哈希，没有原始命令、prompt 或参数值。

## P2 已实现和测试机交付

- 独立标准库 Linux Audit 采集器 `endpoint.audit`，由 `asgp-audit-collector.service` 以 agentsec-lab + adm 补充组运行，MemoryMax=96M、CPUQuota=10%。只读 Audit 日志，可写路径仅端侧私有状态目录。
- 复用已有 UID 1000 的 exec/connect 规则，新增 `/home/agentsec-lab/lab/asgp-p23` 专用文件 watch。未关闭旧项目采集器、未扫描其他用户或 Aegis 诱饵。
- 解析 SYSCALL/PATH/SOCKADDR，丢弃 EXECVE 参数、PROCTITLE 和环境变量。非阻塞 connect 的 EINPROGRESS 记为 in_progress，不能把 syscall 尚未完成写成网络成功。
- 稳定 ID 包含 boot ID、Audit 时间/序号和资源项序号。采集游标与 outbox 在同一事务写入，满队列不推进位点；旋转时先排空仍存在的旧 inode，再读新文件。轮转文件已被删除时报告 rotation_gap，不声称可恢复已不存在的日志。
- 排除 reporter/collector/Hook 自身遥测，防止上报 connect 被反复采集形成反馈循环；已加回归。
- 队列容量满时优先回收已确认 sent 记录，保护 pending；重放不占新槽位；WAL 有被动 checkpoint。主库 32 MiB 门槛和记录数限制不是文件系统硬配额，sessions/WAL/碎片的长期压实仍待实测。
- Hook 可记录产品进程锚点。归因支持精确 Hook ID、带时间边界的进程谱系、显式资源提示加时间的弱候选；保留多候选/冲突，PID 父关系按事件时间推进。归因边保存方法、分数、置信度、证据链和规则版本。
- 新证据形成冲突后，之前 selected 的候选会取消选择；相同事件被其他执行强候选争用时也不强行唯一选择。
- 事件与归因可在 API/主机页面查询，执行时间线能展示经候选边关联的主机事件；源事件仍可没有 execution_id，不改写原始事件来伪造归因。

## P2 证据与限制

两产品真实工具调用各自启动 Python，创建/读取安全 proof 文件并访问本地回环服务。每个探针已知的 process/file/network 三类事件均被捕获，并通过 process_tree 关联到对应 Intent，详见 [运行实测 JSON](p23-runtime-evidence.json)。

Codex 第一次在 workspace-write 下因禁止 socket 而失败；后续仅在非 root 隔离测试账户使用 danger-full-access 执行这条已知无害的本地回环探针。没有改变开发机沙箱或将失败计为通过。Audit 的网络记录为 in_progress，而探针程序自己确认收到 OK，这两种证据保持区分。

本次真实“停 collector → 停隧道 → 后台活动 → 重启 collector → 恢复隧道”验证为：15 条 pending，恢复后全部送达。后台探针没有 Hook 调用证据，不能作为 Agent Intent 归因。见 [离线证据](p23-offline-evidence.json)。

[标注小轨迹](p23-labeled-trace.json)包含 5 条事件（4 条应关联、1 条后台未归因），本次 Precision/Recall 均为 1；它只是合成小样本，不是总体生产准确率。真实两个探针的 3/3 覆盖同样只代表已知探针事件，不代表所有系统调用覆盖或总体丢失率。Audit lost=0 是当时内核累计计数，不代表应用采集链无任何丢失。

P2 尚未全量验收：跨重启/PID 复用的完整身份模型、日志全部轮转删除的断档统计、采集延迟/长期丢失和压力基准、磁盘硬配额、更多正常/攻击标注 trace 与性能测量仍需补齐。当前仅支持 x86_64 b64 的列举系统调用；文件访问不是完整文件内容读取跟踪，未实现 eBPF。

## P3 已开始的可运行范围

- RiskAssessment 分开保存 intrinsic/runtime/exposure，使用每维证据的确定性规则，不直接累加不同引擎分数。运行网络活动只算观测，不直接判外发恶意；exposure 明确是提交上下文，未独立验证。
- PolicyDecision 返回 allow/audit/confirm/block、policy_version、证据引用与理由；不设置为“已生效”。
- 调用审批已接入控制台和设备端，权限新增 govern；viewer 只能读，operator/admin 可治理，设备不拥有控制台权限。
- Admission 的 check 幂等绑定 transaction/content_hash，approve 记录实际操作者；没有真实安装器时 stage/commit/verify/reconcile/rollback 返回 installer_required，不靠客户端布尔值或空状态跳转伪造安装成功。
- Incident 支持调查→确认/误报→处置→复测→关闭/重开；证据引用校验存在性。真实风险关闭必须有关联 Finding 对应检测器/目标的 clean DetectorRun，且复测发生在工单开启后；retest_passed=true 不能替代证据。
- 状态流转以原状态为条件更新并记录操作者、动作和时间，避免并发覆盖；API 沿用请求审计，输入秘密不回显。
- 页面新增调用审批、主机运行事件、归因候选和治理记录；审批页可自动刷新。不是完整的五中心前端。

P3 尚未全量验收：受管安装器的真实 stage/commit/verify/rollback、审批超时与内容漂移的安装事务、风险规则管理、Incident 修复动作与真实复测闭环、多中心 UI 和真实 ASR/Utility/MTTR 等指标还未交付。新增契约/状态机不作为这些能力的验收替身。
