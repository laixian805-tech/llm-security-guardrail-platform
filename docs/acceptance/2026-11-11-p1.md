日期：2026-11-11。主仓库 `/root/agent-security-fusion-platform`；受控端为 `116.62.28.177` 的非 root `agentsec-lab` 用户，开发机只运行控制面，不安装产品 Hook。本报告覆盖本轮开发和实测，不把 P0 的全部历史验收或 P2/P3 视为完成。

## 结论

**Codex 0.166.0 与 Claude Code 2.1.152 均已实际接入 ASGP**，不是 fixture 占位。两产品各自完成 StepFun 真实模型任务、四类 Hook 派发、设备上报和 Execution/Intent 时间线。端侧默认 observe。

Claude 的原生确认已通过接受/拒绝两种产品回执；**Codex 0.166.0 会忽略 Hook ask 并执行工具，不支持原生 confirm**。已在适配器、服务端、能力矩阵、端侧和 UI 上保留该限制：需要确认的 Codex 本地规则按 deny 处理，不能声称“已实现 Codex 审批”。因此原 A1 若要求两个产品都原生 confirm，仍存在明确的产品能力缺口；其余主链路已交付并实测。

## 验证与运行状态

全套测试已包含真实 SkillSpector/Cisco CLI，不再把原先 7 项跳过写成通过；末次完整结果为 **263 passed、0 skipped，66.17 秒**，记录在 p1-evidence.json。另有 fixture E2E：两产品实际 endpoint CLI → 临时 HTTP 控制面 → 2 个 Execution/2 个 Intent → 稳定重放零新增 → 吊销后的 dead 队列。这个 E2E 的产品输入来自版本化录制，证据等级与上面的真实产品执行分别记录。

端侧 10 次合成安全 payload 的实际进程启动/SQLite 持久写入中位约 79 ms，最大约 97 ms，无网络等待；不是端到端 SLA。开发机排查后内存保持有余量，控制面约几十 MiB，reporter 约 10 MiB；两端服务均有限额和失败重启。

运行服务为开发机 asgp-control-plane/asgp-test-tunnel，测试机 asgp-endpoint-flush。服务配置模板见 `deploy/systemd/`，私有配置和凭据不在模板内。控制面已在迁移前 SQLite backup 后升级，回滚见 [runbook](../runbooks/p1-hook-onboarding.md)。

## 尚未验收或未实现

- Codex 原生 Hook confirm：当前版本不具备，不能按原 A1 字面写成全通过。未来若产品提供真实确认通道，再新增版本能力与回执证据；不能用字符串协议猜测替代。
- P0 全部五种引擎/讯飞/公网生产部署的完整验收仍未收口；StepFun 已单独补实测成功。
- Hook 失败、解析失败、进程超时和队列容量门槛可能导致漏观测；默认 observe，不能作为 OS 强制执行边界。
- 队列有记录数/主库大小/重试/保留门槛，但 sessions 元数据、WAL、数据库压实和文件系统硬配额仍需补强；当前不宣称完整磁盘资源治理。
- 安装器检测用户配置变化后拒绝自动覆盖；需要保留备份人工合并。端点状态对同一用户不防篡改。
- 未实现 Linux Audit/eBPF 主机采集、因果归因、风险聚合、中央策略审批、准入事务、Incident 或 EnforcementEvidence 存储。端侧测试规则不是完整策略引擎。
- 真实决策实验用短任务和无害 proof 文件；有的 app-server 探针由测试程序终止或合成延迟探针未发送 SessionEnd，控制面保留 running，不伪造为 completed。
- 当前为单测试端、SSH 隧道拓扑；多租户生产入口、mTLS、证书管理及网络级强制策略需另行实现。
