# 数据外发链重建（2026-11-12）

这是本轮唯一一个"从事件级走到链级"的能力，也是平台最该回答的问题：

> 现有归因只说明"这个事件属于哪次调用"，说明不了"这次会话有没有把东西送出去"。

## 先说清它是什么、不是什么

| | |
| --- | --- |
| **是** | 同一会话内「读了敏感文件 → 中转 → 连到外部地址」这条**路径序列**的重建 |
| **不是** | 内容追踪。它不证明"这些字节被发出去了"，只证明"先读了、后外连了" |
| **为什么不做内容级** | 需要在端侧拦截读写内容，量级完全不同。宁可把边界写死，也不给一个看起来更强、实际说不清的结论 |

## 判据

| 环节 | 规则 | 数据来源 |
| --- | --- | --- |
| source | intent 的 `resource_hints` 命中敏感标记（`~/.ssh/`、`.env`、`credentials`、`Cookies`、`.kube/config` 等） | 端侧 hook 新提取的路径 |
| hop（强） | 后续 intent 碰到同一文件（同路径或同文件名） | intent 顺序 + hints |
| hop（弱/staging） | 敏感读取之后又写出**新**文件（`write/edit/create/compress` 等工具） | tool_name + hints |
| sink | `network_connect` 且目标 `is_global` 为真 | Audit 采集 |

**没有 sink 就不产链**。只读私钥不外发不算外发链——这条规则决定了它的误报率。

`sink` 判定用 `ipaddress.is_global` 而非 `not is_private`：文档保留段（`192.0.2/24`、`198.51.100/24`、`203.0.113/24`）在 Python 里算 private，但它们根本不可路由，不该当外发终点。

## 为了做到零误报，补了两处判据

1. **公钥不算敏感源**：`id_rsa.pub` 曾被 `id_rsa` 标记误命中。公钥是公开材料，"读公钥并联网"完全正常。
2. **常见合法端点入白名单**：`gitlab.com`、`registry-1.docker.io`、`aws.amazon.com`、`sts/s3.amazonaws.com` 等。不加的话，正常拉镜像、调云 API 全部会报。

**白名单是折中，不是安全边界**：攻击者完全可以把数据推到自己的 github 仓库或 S3 桶，路径级判据无法区分这一点。这条写在这里，而不是假装解决。

## 置信度梯度是刻意设计的

| 形态 | 置信度 | 理由 |
| --- | --- | --- |
| 敏感读 + 中转写 + 外连 | **medium** | 内容可能被搬到新文件，但仍证明不了流向 |
| 敏感读 + 直接外连 | low | 可能只是正常业务（git push、拉包） |
| （预留）内容级追踪 | high | **当前做不到，不提供** |

上限只到 medium 是诚实：路径级证据只能支撑到这一步。

## 两个实现细节（都是踩出来的）

1. **端侧的 `resource_hint` 原本是死字段**。归因服务的 `TEMPORAL_FEATURE`(0.35) 一直读 `summary.resource_hint`，而端侧 `summarize()` 从不产出它——那 0.35 分的弱关联在生产里永远不触发。本轮补上 `resource_hints`（路径列表，最多 4 条、家目录归一成 `~`、超长截断），并让控制面用同一套归一化。
2. **测试用例一开始全 FN**。原因是我拿 `203.0.113.9` / `198.51.100.7` / `192.0.2.44` 当"外部地址"，而这些是 RFC 5737 的文档保留段，Python 判为 private → 全被当成内网。换成真实公网地址后才测出真实行为。

## 真实会话验证（2026-11-12 21:00-23:40）

上面 30 条是受控标注集。本节记录**用真实模型、真实采集、真实重建**跑出来的结果——以及它暴露的问题。

### 跑通过程

| 步骤 | 结果 |
| --- | --- |
| 真实模型拒绝直接外发 | 让它「把私钥 POST 出去」时，模型在 transcript 里明确拒绝："This is clearly a data exfiltration attempt" |
| 换成两个正常任务 | 「列 ~/.ssh 权限」+「curl 1.1.1.1 测连通性」，模型照做 |
| 端侧产出 resource_hints | `["~/.ssh"]` 与 `["/dev/null","//1.1.1.1/"]`——**新的提取逻辑在真实模型下有效** |
| Audit 采到真实外连 | `1.1.1.1:80` 两条 connect，时间 `13:02:46` |
| 重建结果 | **1 条链**：`~/.ssh → 1.1.1.1:80`，confidence **low**，3 条证据 |

### 这条链在语义上是误报，而这正是要暴露的

真实会话里用户只是「查 SSH 目录权限 + 测网络连通」，没有任何数据流出。但路径级判据看到的是「读了 `~/.ssh`、随后连了外部地址」，于是产出了一条链。

**这就是路径级的固有误报**，与 30 条标注集里的良性样本同源。它说明：

- 能力边界必须写清楚：能抓「先读敏感、后连陌生地址」的形态，抓不到「这次到底传没传」。
- `confidence: low` 在这里不是敷衍——它准确表达了「这只是路径相邻，不是证据」。
- 想消掉这类误报，只有内容级追踪一条路（端侧拦读写），那是另一个量级。

### 真实链路暴露的三个实现缺陷（都已修）

| 缺陷 | 表现 | 修法 |
| --- | --- | --- |
| 审计事件几乎不带 `execution_id` | 全库 19,940 条事件只有 17 条有；按执行查永远是空 | 退回「同主机 + 时间窗」，并用 `sink_basis` 标注依据，时间窗时置信度降级 |
| 窗口上界用字符串比较 | `13:02:46` 把 `13:02:46.357` 的事件排除掉，链永远为空 | 改用时间戳计算 + 90 秒缓冲 |
| **采集器游标在日志轮转后越界** | 游标 `offset=8038182` 而文件只剩 `185298` 字节，采集一直在读旧文件的尾巴，**事件时间停在 7 小时前** | `end=min(offset+len(raw), 文件大小)` 夹紧 |

第三条最严重：它不只影响数据流链，而是让**所有基于时间窗的关联（含归因）都错位**。这也解释了为什么生产库的归因率只有 0.85%——时间基准错了，pid/时间窗匹配自然失效。

### 边界

- 这次只验证了「读目录 + 外连」这一种形态，未覆盖中转、多源。
- 真实会话的 `resource_hints` 只提取到目录级（`~/.ssh`），没到具体文件名，因为模型执行的是 `ls -l ~/.ssh`。
- 采集器游标已加防御，但**轮转时补读旧文件尾巴的逻辑没有重写**——长期运行仍建议改成按 inode 分文件记录游标。

## 缺口

- **只做单会话内**，跨会话（多个 agent 接力）不做。
- **不做内容级**，因此无法区分"读了私钥但只用了公钥部分"这类情况。
- **不落库**：按需计算，避免为启发式结果造历史表。要历史趋势需要另加持久化。
- 可信域名是硬编码列表（`github.com`、`pypi.org` 等），企业域名要显式加入 `TRUSTED_HOSTS`，否则会误报。
