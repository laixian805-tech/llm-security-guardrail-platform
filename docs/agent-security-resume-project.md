## 3. STAR 深度叙述

**Situation**：企业员工在办公终端和开发机广泛使用 AI Coding Agent、MCP Server 与 Skills，风险从模型输出内容扩展到本机权限、工具执行、凭证使用和数据流转；现有 EDR/HIDS 看不懂 Agent 语义，工具调用和供应链侧缺少控制点。

**Task**：负责 Agent 运行时防护的落地运营——建设检测策略、调查安全告警、验证控制有效性。

**Action**：

- 设计并运营 28 项检测策略，覆盖指令投毒、危险命令执行、敏感文件与凭证访问、数据外发、MCP 越权、供应链风险、Hook 配置篡改、进程环境异常 8 类风险场景。
- 搭建安全告警场景的多 Agent 编排流水线：按资产、网络、身份分域调查，多源证据交叉核验后定性。
- 推动 Hook（工具执行前检查）+ 终端行为监控（auditd/eBPF）+ MCP 审计的分层控制落地，明确各控制点覆盖边界与盲区。
- 建立误报治理闭环：按 matched signals 归类误报、修订规则、回归验证。

**Result**：近一个月检出 300+ 起真实风险事件，告警有效率 85%；形成"资产发现 → 运行时监控 → 策略控制 → SOC 运营"方法论，并在个人环境完整复现为可运行系统。

## 4. 检测策略体系讲法（28 / 8）

面试被问"你的 28 项策略是什么"时，按 8 类讲，每类举 1–2 个代表策略并说明定级理由。完整表见落地文档第 8 节。参考讲法：

> 我不是按工具名列规则，而是按风险场景分层。比如敏感凭证访问这一类，Hook 层在 PreToolUse 拦路径（S08），Monitor 层兜底子进程读取，两条证据互相印证；危险命令里 `curl|bash` 直接 block，`sudo` 要 ask，因为误杀成本高。28 项里 critical 只占三分之一，其余是 alert/audit，保证告警可运营——这也是有效率 85% 的主要来源：分级而不是一刀切。

## 7. 面试高频问答

**Q1：Hook 和 EDR 有什么区别？为什么两个都要？**
Hook 在 Agent 语义层，看得懂工具名和参数，能在执行前阻断，但依赖产品支持、有覆盖盲区（Bash/Python 子进程、MCP 写文件）；EDR/auditd 在系统层，能看到真实执行行为但不懂 Agent 意图。所以 Hook 做前置检查，Monitor 做兜底和交叉验证——同一行为两侧都命中就是高置信证据。

**Q2：只配 `Write|Edit` 的 Matcher 够吗？**
不够。覆盖范围 = 事件支持能力 × Matcher 配置 × 实际执行路径。Agent 用 Bash 重定向或 Python 子进程写文件时这条规则不命中，需要 Bash 规则和进程/文件监控补。我在个人项目里专门画了覆盖矩阵（落地文档 4.5 节）。

**Q3：28 项策略怎么定级、怎么防误报？**
按"确定性 × 影响"定级：确定性高且影响大的（`rm -rf`、读 `.ssh`）直接 block；影响大但误伤成本高的（`sudo`、生产操作）ask；其余 alert/audit。每条策略输出 matched signals 和 reason，误报可归类、可回归，这是 85% 有效率的主要来源。

**Q4：300+ 事件里有效事件长什么样？**
主要是三类：Skill/MCP 里的隐藏指令和诱导描述、Agent 会话读取敏感路径或打包源码、未登记 MCP server 启动。每类都落到具体规则和证据链，调查时按分域取证交叉核验。

**Q5：个人项目和企业实习什么关系？**
方法论来自实习：控制点分层、事件模型、检测策略目录都是企业环境验证过的。个人项目是把同一套东西在我自己的设备上从 0 实现，证明我不只会用平台，也能建平台。数据不混用：实习的数据是企业的，个人项目的数据是我自己机器上跑出来的。

**Q6：MCP 安全你觉得最核心的风险？**
三个：工具描述投毒（诱导模型调危险工具）、filesystem 越权（路径逃逸到 allowlist 外）、Confused Deputy（server 用高权限身份执行低权限请求）。对应 S03/S14/S15 和注册审批。

**Q7：如果 Agent 绕过 Hook 怎么办？**
承认 Hook 不是万能的，所以有 Monitor 兜底；更进一步把"防护失效本身"当事件监控——Hook 配置被改、回调脚本被换、guard 失联都告警（S21–S23）。个人环境还要接受一个事实：本机高权限账号能绕过一切本机控制，企业版要靠托管配置和 EDR 补齐。

**Q8：事件模型怎么设计？**
统一 schema：source / event_type / host / session / agent / tool / target / decision / severity / evidence。关键设计是 `session_id` 贯通：Hook 在 SessionStart 把 session_id 写进进程环境，Monitor 沿 ppid 链继承，这样工具调用、进程、文件、网络能按一个会话回放。

**Q9：为什么用 SQLite 不用 ELK？**
个人规模 SQLite 足够且零运维；边缘设备本地缓冲、断网重传。事件模型按可迁移设计，字段口径和 SIEM 对齐，企业版直接进 Kafka/SLS。

**Q10：这个项目和你的 GuardBench 评测项目什么关系？**
一个是"运行时"（Agent 在真实设备上做什么），一个是"模型层"（模型被注入后的行为）。两者共享事件模型和 allow/block/audit 动作枚举；Runtime Guard 的判定逻辑就是策略层的同一个函数。
